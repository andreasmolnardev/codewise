# Dev Container support

The environment manager can use a repository's Dev Container configuration when it provisions a worker. It discovers `.devcontainer.json`, `.devcontainer/devcontainer.json`, and `.devcontainer/<name>/devcontainer.json`. If the worktree has no configuration, it uses `SUBPOLAR_WORKER_IMAGE` as the default image.

When a worktree contains one configuration, the manager selects it automatically. When it contains several, set `SUBPOLAR_DEFAULT_DEVCONTAINER_CONFIG` on the manager to the selected repository-relative path, for example `.devcontainer/api/devcontainer.json`. In the Compose deployment, pass it through the same-named environment variable. The selection applies to each managed worktree handled by that manager.

The supported configuration accepts either a literal `image` or a `build` object containing only `dockerfile` and optional `context`, plus optional `containerEnv`, `workspaceMount`, `workspaceFolder`, `postCreateCommand`, `postStartCommand`, `name`, and `$schema` metadata. `containerEnv` accepts literal string values only; host interpolation and overrides for `HOME`, `TMPDIR`, or `SUBPOLAR_RUNTIME_DATA_DIR` are rejected. A custom `workspaceMount` may bind only the current worktree to a dedicated normalized path inside the manager's workspace namespace, with an optional consistency hint. It is unavailable for linked Git worktrees, whose Git metadata pointer depends on the default container path. `workspaceFolder` must be a normalized path inside that workspace mount. Lifecycle commands may be shell strings or argv arrays. `postCreateCommand` runs from `workspaceFolder` (or the worktree root) and successful runs are recorded in the private runtime data volume, so retries do not repeat completed work. `postStartCommand` runs from the same directory after each stopped-to-running transition. A failed hook stops the worker and fails startup. JSONC comments and trailing commas are accepted. Dockerfile paths and build contexts must resolve inside the worktree; the manager maps them to the Docker host workspace and builds the image itself. The manager continues to apply its configured CPU, memory, and process limits, an unprivileged user, a read-only container root, no network, dropped capabilities, and only the verified worktree and optional Git metadata mounts.

Compose configurations are disabled by default because containers on a Docker bridge may still reach services exposed by the Docker host. An administrator can opt in on the manager with `SUBPOLAR_ENABLE_DEVCONTAINER_COMPOSE=true`; this does not block access to host services and is a residual isolation boundary. Enabled configurations may name one Compose file and must select one app `service`. The app may use a literal `image` or a contained `build` with only `context` and `dockerfile`, plus a literal `environment` map. It may use the current worktree only through `workspaceMount`; Compose service volumes, host ports, custom networks, commands, privileged options, and all other service settings are rejected. A Compose file may add one PostgreSQL service, selected in `runServices` and referenced by the app's `depends_on`. It must use a tagged or digest-pinned `postgres` image, a literal `POSTGRES_PASSWORD`, optional `POSTGRES_DB` and `POSTGRES_USER`, and only the manager-owned `subpolar-data:/var/lib/postgresql/data` volume. The manager creates a per-environment internal Docker network, attaches only the selected app and PostgreSQL containers, and applies resource caps, read-only roots, dropped capabilities, and no published ports. It starts and health-checks PostgreSQL before the app, stops both together, and removes the database volume only when the environment is explicitly removed. `workspaceMount` and Compose are unavailable for linked Git worktrees.

OCI and local Dev Container Features are built with the official Dev Container CLI 0.89.0. Feature builds require a valid root `.devcontainer-lock.json`; the manager invokes the CLI in frozen-lockfile mode so a feature resolution change fails provisioning instead of silently changing the build. Each exact feature reference must also appear in the manager's comma-separated `SUBPOLAR_ALLOWED_DEVCONTAINER_FEATURES` setting. The manager image pins a Node 22 Alpine base by digest for this CLI. Image-based and Dockerfile-based Features use the same manager-owned image build path, then the manager runs the configured lifecycle hooks inside the isolated worker.

The manager rejects other Dev Container properties, including build args and targets, `remoteEnv`, arbitrary mounts, port declarations, and privilege requests. A rejected configuration fails provisioning with a specific error; the manager does not silently switch to the default image.

This is staged Dev Container support, not full Dev Container CLI compatibility. The official CLI is used only for feature image builds; plain Dockerfile configurations use the host Docker CLI. Build output is included in manager logs. Images and Dockerfiles must work with the manager's fixed worker user, filesystem, and network settings. The manager does not run the CLI's `up` command, so worker isolation and lifecycle remain under manager control.
