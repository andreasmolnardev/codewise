## Ownership

T3 owns threads, conversation history, orchestration events, provider lifecycle, project worktrees, Git operations, checkpoints, terminals, previews, and client protocol. Subpolar may supply runtime composition, Pi execution, tools, policies, and approvals. A Subpolar runtime session is referenced by a T3 provider session; it does not replace T3's thread or event state.

The first migration increments import the runtime contracts, policy gateway, transient Pi adapter, tool registry, runtime host, ACP bridge, and a backend-neutral environment manager contract under `packages/subpolar-*`. They do not add client UI, RPC methods, event schemas, a new provider kind, or a competing persistence store. The T3 CLI manages profile catalogs and selection in the private `<T3 stateDir>/subpolar-agent-profiles.json` file, scoped to ACP provider instances. The server validates the file, resolves only the selected profile, and passes bounded non-secret profile data to local ACP or the managed worker. The pure profile resolver still supports model selection, tool allowlist intersection, and restrictive tool-policy composition. Profiles have no T3 UI, RPC, or project/environment binding yet. T3's native Pi provider remains available. Managed execution must be opt-in and fail closed if its runtime is unavailable.

This is a partial integration. In managed-worker mode, the ACP session ID is mapped to a hashed Pi session ID stored in the manager-owned runtime volume. ACP load and resume validate that persisted state exists and belongs to the requested session and working directory; missing or mismatched state fails closed. Warm and cold resume restore Pi's native branch while T3 remains authoritative for conversation history and orchestration events. T3 persists a Subpolar provider-session binding with the ACP session ID, Pi session ID, thread, and provider instance after the ACP thread is ensured, and marks the record stopped or errored when that runtime closes. This record is an index only: runtime recreation does not yet read it to adopt manager handles or recover output cursors, and run outcomes and events are not persisted or replayed by Subpolar. The ACP registry can collect bounded string form fields, including secret fields, through T3's existing credential interaction. When `Use T3 managed Pi credentials` is enabled and an allowlisted `Pi provider ID` is configured on an ACP provider instance, its sign-in methods include `Pi provider credential`. An operator can select that method and paste a Pi `api_key` or `oauth` credential JSON object into T3's masked credential prompt. The server validates and stores the record in that instance's encrypted `ProviderHost.credentials("subpolar-pi", instanceId)` entry. The worker receives only the scoped private ACP CredentialStore bridge, bound to its active session and T3 thread; credential values stay out of worker environment, files, arguments, transcripts, and protocol logs. Refresh writes go back to that same instance entry. The bridge has a same-process per-instance write lock, but the backing credential API has no compare-and-set, so multiple T3 server processes sharing a credential backend could race.

Managed Pi model requests are opt-in through `Enable managed Pi model requests` on the same ACP provider instance. T3 services requests through a private ACP extension bound to the active session and configured Pi provider ID. The worker stays on Docker's `none` network; it cannot open provider sockets itself. The T3 host sends HTTPS only to the fixed public API host registered for that Pi provider ID, resolves and pins a public IPv4 address for each request, rejects redirects and non-HTTPS/custom endpoints, and caps request and response bodies. HTTP providers that honor Pi's per-request `fetch` option can use this path. The first allowlist includes Anthropic, DeepSeek, Google Generative Language, Groq, Mistral, OpenAI, OpenRouter, and xAI. Providers using WebSocket transports, Google Vertex, custom endpoints, other provider IDs, model catalog refresh, and deferred model operations are not supported by this path and fail closed. Since response bodies are buffered before returning over ACP, long streams may be slower and hit the response cap. The outbound request still originates from the T3 host, so the host must have network access to the configured provider API.

## Integration boundary

T3's refreshed server uses the `provider-acp` and `provider-acp-registry` packages and orchestration-v2. Its existing ACP registry provider accepts a local executable path and arguments, so `@subpolar/acp` uses that path without a new provider kind or driver registration. By default, the bridge delegates prompts through `@subpolar/runtime-host`, which composes the Subpolar stateless runtime and Pi adapter. Without persistent runtime storage, sessions and transcripts are process-local. In managed-worker mode, Pi's native session files persist in the environment volume and can be reopened by ACP session ID; T3 run outcomes and event replay remain unsupported. When manager URL, token, and storage root are configured for the T3 server, local mode exposes one argv execution tool through the authenticated environment-manager client; every call requires T3's one-time ACP approval. With those settings unset, local mode exposes no tools. Set `SUBPOLAR_ACP_EXECUTION=managed` to use the authenticated non-TTY process transport instead: the bridge starts one configured worker command for each ACP session, forwards ACP requests, updates, and client callbacks, and returns worker startup failures without falling back to a local runtime. The bundled worker image includes the ACP/Pi runtime. When it runs with the proxy's explicit worker flag, it exposes a workspace-bounded argv execute tool whose permission requests flow back to T3; it inherits no manager token, caps output, and supports cancellation. With the hidden broker setting enabled and provider IDs allowlisted, the worker can read and refresh instance-scoped Pi credentials through its active ACP session; it cannot access T3 state or the Docker socket. Model egress is separately opt-in and currently limited to the fixed HTTP provider endpoints described above; real managed Pi turns still need end-to-end validation.

`@subpolar/environments` provides stable owner/workspace/worktree identities, canonical path containment checks, per-environment lifecycle/reconciliation serialization within one process, an optional local registration store, and an injected backend contract. The local store persists environment metadata with restrictive file permissions and reconciles registrations after manager restart. Its Docker adapter validates resource labels/configuration on lifecycle operations and maps a worktree to a writable bind mount. For linked Git worktrees it can additionally mount only the verified common Git directory when explicit gateway and Docker-host Git roots are configured. A separate manager-owned volume stores Pi agent configuration and session files outside the worktree; it survives rebuilds and is deleted only on explicit removal. Exact legacy configurations can be migrated; unexpected configurations fail closed. The Docker Engine client runs in a dedicated authenticated manager process, while workers receive neither the Docker socket nor Docker CLI. The process runner uses `docker exec -i` with a packaged supervisor, streams output, and terminates owned process groups on cancellation or stream loss. Compose supplies explicit gateway and Docker-host workspace paths, which must resolve to the same underlying data. Manager and worker image behavior has been tested with Docker Desktop, including the app-to-PostgreSQL path in an isolated per-environment Compose network. A focused Docker smoke on 2026-10-19 also built the current manager and worker images and provisioned two disposable Git workspaces as separate `networkMode=none` workers. Managed processes returned output and exit codes, each worker could write only its own workspace marker, the manager-owned runtime volume survived worker stop/start, and both registrations survived a manager container restart. An outside-root worktree request failed with `WORKTREE_OUTSIDE_ROOT` and did not add a registration. The Docker Desktop PTY attach path returned HTTP 101 through the socket proxy; non-TTY managed stdio worked. The gateway token wiring and empty health response have focused coverage. Docker Desktop failed with an image-layer I/O error while unpacking the rebuilt gateway; GitHub Actions run 39262577317 is queued for the current source commit. Gateway startup and state/workspace persistence still need a restart round trip.

The ACP bridge is now a workspace dependency of the T3 server, so an operator can configure it through T3's existing local ACP command setting. For a source checkout, the command can be Bun with `packages/subpolar-acp/src/cli.ts` as its argument. This makes the ACP entry point available without adding a provider kind or changing the client protocol; it does not configure a Subpolar provider automatically. To provision Pi credentials, edit that provider instance's settings, enable `Use T3 managed Pi credentials`, set `Pi provider ID` to the exact Pi provider key (for example `openai`), save, then choose `Pi provider credential` in its sign-in flow and submit the Pi credential JSON. The secret stays in T3's encrypted provider credential storage. The bridge process and Pi SDK still run on the T3 host in local mode; only its approved argv execution tool uses the manager. Managed worker Pi sessions can resume after worker restart when their runtime volume survives. Managed model requests can be enabled separately for the supported, fixed HTTP provider endpoints described above; an integrated T3 thread turn still requires end-to-end validation.

The environment package exposes an authenticated HTTP manager and admin CLI for status, list, inspect, lifecycle, and reconciliation operations. A host-injected, authenticated read-only tool-catalog HTTP adapter now defines the Subpolar CLI list/describe contract, but T3 does not mount it until a T3-owned catalog service and read authorization binding exist. Gateway-to-manager HTTP is allowed only on loopback by default; private Compose hostnames require the explicit `SUBPOLAR_MANAGER_ALLOW_PRIVATE_HTTP` opt-in, and remote managers should use HTTPS. T3 can route approved ACP argv tools and opt-in terminals for provider IDs listed in `SUBPOLAR_MANAGED_PROVIDER_INSTANCE_IDS`. Setup scripts for those allowlisted provider instances use the same managed terminal path. Managed terminal routing preserves T3's existing terminal protocol. Server-browser previews running in T3's server runtime also support localhost ports for explicitly allowlisted ACP provider instances. For each localhost browser request, T3 resolves the thread's current provider instance and worktree, then routes through a local listener backed by the existing manager TCP port tunnel in that environment. This uses T3's existing preview endpoint and protocol; an empty allowlist does not install preview interception.

In local mode the ACP bridge and Pi runtime execute in the T3 gateway process, while only its approved argv tool runs in the worker. Managed mode runs the ACP/Pi runtime inside the worker and can use the instance-scoped credential broker and opt-in model egress after credentials have been provisioned. T3 Git operations still run on the gateway. The manager can open a byte tunnel to a selected loopback TCP port in one exact worker environment while the worker stays on `networkMode:none`. For server-browser previews, T3 binds that tunnel to the thread's current worktree and selected allowlisted provider instance on each localhost request. If the thread is missing, the worktree is invalid, the instance token is unavailable, or tunnel setup fails, T3 aborts the request rather than letting managed preview traffic reach the gateway's localhost. The focused `SubpolarPreviewRouting.test.ts` passed 2/2 tests using a fake manager: it checks routing to distinct worktrees, HTTP byte forwarding through the local tunnel, and fail-closed target resolution. It does not exercise a Docker-backed manager or a browser end-to-end flow. There is no cross-process registration transaction, Docker container enumeration/orphan cleanup, or distributed lock; the optional JSON registration store is suitable for a single manager process. The focused Docker smoke described above also exercised the authenticated manager's non-TTY stdio session, manager registry recovery, and worker data volume persistence. It did not verify PTY attach on Docker Desktop, which returned HTTP 101 from the socket proxy. A composite test in `AcpAdapterV2.test.ts` connects T3's generic ACP adapter to the managed ACP proxy and a fake environment manager/worker, then checks a mock Pi turn, T3 permission acceptance, worktree cwd, and worker termination. It passes, but does not exercise a Docker-backed worker, a real Pi runtime, or the full event-source/client path. Gateway startup and gateway persistence through the production image remain unverified. The terminal adapter is available only when explicitly configured and must not be described as complete managed agent isolation.

The Docker backend discovers Dev Container configurations at the worktree root and `.devcontainer/`, including named configs. A single config is selected automatically; multiple configs require the manager's `SUBPOLAR_DEFAULT_DEVCONTAINER_CONFIG`. It supports literal images, contained Dockerfile builds, locked and allowlisted Dev Container Features, literal `containerEnv`, constrained workspace bind mounts/folders, and `postCreateCommand`/`postStartCommand` hooks. Compose is disabled by default and requires the manager's `SUBPOLAR_ENABLE_DEVCONTAINER_COMPOSE=true`; the accepted subset is one app plus an optional PostgreSQL service on a manager-owned network and volume. Host services may still be reachable from that Compose network, so enabling it is an administrator trust decision. See [Dev Container support](dev-containers.md).

The manager exposes authenticated non-TTY process sessions with stdin forwarding, sequenced stdout/stderr events, reconnectable output, and process-group termination. The managed ACP proxy uses this transport. The bundled worker image includes the Subpolar ACP bridge and Pi SDK; its local Docker build has been verified.

## Source disposition

Subpolar's existing frontend and `@subpolar/client` are not imported. Its application backend is not copied wholesale because it combines Bun APIs, PocketBase, profile/session routing, tools, Git, and old UI concerns. Persistence, automations, browser services, and external-agent adapters remain deferred until they can be adapted without duplicating T3-owned state.
